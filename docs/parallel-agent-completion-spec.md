# ТЗ: завершение прогнозирующего агента параллельными задачами

Дата: 2026-09-23. Проверенная база: локальный `main`, `66421cf`.
Основание: [условия кейса](hackalem-ai-agentic-wind-forecasting.md).

## Цель и исходное состояние

Замкнуть путь: архивный погодный прогноз → проверенные входы → обученная модель → почасовой прогноз 24/48 ч → анализ → новая версия при обновлении входов → февральская оценка.

Уже существуют production agent runtime, PostgreSQL jobs, checkpoints, retries, fencing, replay, импорт CSV и persistence inference. Не реализовывать их заново. Старые аудиты `agent-system-problems.md` и `agent-subsystem-remediation-spec.md` описывают более раннее состояние; фактический код имеет приоритет.

Главные разрывы: внешний weather connector не наполняет canonical weather tables; обученная модель не подключена к production; отсутствует завершённый автоматический цикл обновлений и воспроизводимый февральский E2E; февральских actuals нет. Страница history интегрирована другим исполнителем в `66421cf`: просмотр сохранённых выпусков уже есть, запуск полного периода остаётся отдельной задачей.

## Правила параллельного исполнения

1. Задачи P1–P6 можно запускать одновременно, каждую — отдельному исполнителю в отдельной ветке/worktree от актуального локального `main`. Исполнитель сначала читает AGENTS.md, STATE.md и настоящий документ, проверяет существующую реализацию.
2. Каждая задача владеет только указанными путями. Чужие задачи, общий README, package.json, существующие общие типы и миграции не менять. Новые команды запускать напрямую через имеющиеся Node/tsx. Общее wiring принадлежит P6.
3. Публичные границы ниже фиксированы. Для незавершённого соседа использовать тестовый adapter по контракту; он не должен становиться production fallback. Не создавать вторую очередь, второй формат прогнозов или альтернативную БД.
4. Код задач можно интегрировать в любом порядке, но их результаты не объявлять общим E2E до P7. P6 сначала делает модули с dependency injection; конкретные импорты соседей подключаются после их появления. В каждом промежуточном коммите приложение обязано собираться.
5. Проверки, ограничения и следующий шаг фиксировать в `docs/handoffs/parallel-PN.md`. STATE.md согласовывать при последовательной интеграции, сохраняя сведения о других активных задачах.
6. Не изменять чужой грязный worktree, не stash/reset/clean чужие изменения. Недоступные данные отмечать BLOCKED, не заменять синтетикой без маркировки.

## Контракты между задачами

- Использовать существующие `src/server/contracts/index.ts`, `AgentPorts`, `ForecastInputSnapshot`, `JobPayload`, формат ML artifact. Имена полей и единицы не дублировать новым несовместимым DTO.
- Все абсолютные времена — UTC ISO, target = issuedAt + leadHour, leadHour = 1…24/48. Настройка календаря выпуска содержит явную IANA timezone; её нельзя молча вывести из локального времени ОС.
- Только информация с доступностью не позже issuedAt попадает во входы. Февральские цели из evaluation-only хранилища запрещены в обучении, выборе модели и признаках.
- Единица результата — `normalized`. MW/MWh и суммирование рядов возможны только после подтверждённой семантики.
- P1 сохраняет погоду в существующие `raw_artifacts`, `weather_runs`, `weather_values`. Полный run виден потребителю только после успешной транзакции. Событием для P3 служит запись run в БД; отдельный callback между задачами не требуется.
- P2 экспортирует `predictApprovedModel(request, snapshot, artifact)` из `src/server/ml/inference/index.ts`: Promise существующего типа значений прогноза, того же, что возвращает persistence. Artifact проверяется по существующей схеме; утверждение модели, checksum и версия обязательны. Точный TS-тип вывести из текущего persistence, не вводить произвольный record.
- P3 создаёт существующий durable agent job через существующий store. Payload не меняется; event key детерминирован по объекту, issuedAt, горизонту, версии модели/config, версии входов и режиму. Replay и live не смешиваются.
- P4 работает через существующие agent/replay API и читает canonical forecasts; не вызывает новую приватную ML-функцию напрямую.
- P5 читает сохранённые forecasts и изолированные actuals. Возвращает существующий формат evaluation; `N=0` означает отсутствие метрик с причиной, а не нулевую ошибку.
- P6 — единственный владелец изменений `src/server/agent/**`, `src/server/forecast/**`, dashboard client и deployment wiring. P1–P5 предоставляют модули/артефакты, не редактируют эти пути.

## P1 — Достоверная погода в PostgreSQL

Ветка: `feat/p1-weather-ingestion`.
Владение: `src/server/connectors/weather/**`, новые `scripts/weather-ingest.*`, `tests/weather/**`, `docs/handoffs/parallel-P1.md`. При необходимости только новая миграция с уникальным префиксом `0101_p1_`.

Работа:
- Расширить существующий connector: получить архивные forecast runs по координатам и требуемому горизонту; записать raw artifact/hash, значения, provider/model/run_time/published_at/available_at/fetched_at.
- Не выдавать reanalysis/actual weather за прогноз. Не считать fetched_at доказательством исторической публикации. Неизвестную публикацию хранить как неизвестную; официальный исторический режим должен явно блокироваться. Исследовательское допущение фиксировать отдельно и исключать из официального отчёта.
- Идемпотентный повторный импорт; проверка координат, единиц, часов, дублей, неполного горизонта; безопасный retry при временном сбое провайдера.
- CLI для загрузки выбранного диапазона и отчёт о покрытии по каждому объекту/выпуску.

Приёмка: PostgreSQL integration доказывает atomic write/rollback, отсутствие дублей, выбор run через текущий PostgresAgentPorts и отклонение будущей/неподтверждённой погоды. Live network smoke отдельный и необязательный для unit suite. Если архив недоступен — connector и проверки завершены, исторические данные BLOCKED с точной причиной.

## P2 — Обученная модель и production inference

Ветка: `feat/p2-trained-inference`.
Владение: `src/server/ml/**`, `tests/ml/**`, новые `scripts/train-approved.*`, `docs/handoffs/parallel-P2.md`.

Работа:
- Переиспользовать ridge, power curve, features, temporal validation и artifacts. Реализовать указанную inference-функцию с persistence как явным baseline.
- Обучать/выбирать модель только на данных до февраля. Проверить соответствие training features реальным доступным forecast features: нельзя обучить на фактической погоде и молча считать это проверенным forecast-сценарием.
- Зафиксировать feature order, scaling, cutoff, training snapshot/hash, code version, temporal folds, baseline metrics и выбранные параметры в artifact.
- CLI выдаёт artifact и отчёт; если выигрыш над baseline не подтверждён — честный результат, без принудительного approval.

Приёмка: воспроизводимость обучения, одинаковая подготовка train/inference, полные 24/48 точек, invalid/missing feature и неподдерживаемый artifact отклоняются. Контролируемый тест показывает чувствительность обученной модели к погодным признакам. Февральские targets не участвуют в подборе; сравнение с baseline на дофевральской валидации приложено. Wiring в agent делает P6.

## P3 — Автоматические триггеры и восстановление

Ветка: `feat/p3-input-triggers`.
Владение: новые `src/server/triggers/**`, `scripts/input-trigger-worker.*`, `tests/triggers/**`, `docs/handoffs/parallel-P3.md`; новые миграции только `0103_p3_`.

Работа:
- Worker обнаруживает новые полные weather runs и релевантные версии observations, ставит существующие jobs; период опроса и объекты заданы конфигурацией.
- Cursor/event ledger в PostgreSQL; постановка и фиксация обработки атомарны либо используют идемпотентную схему, исключающую потерю события.
- Явная политика issuedAt: запланированный выпуск либо пересчёт того же выпуска допустимыми на его момент входами. Новые данные из будущего нельзя подставлять в старый issuedAt.
- Повтор события — без дубликата; новая версия допустимых входов — новый расчёт; replay изолирован от live.

Приёмка: два worker одновременно, повтор события, crash до/после enqueue, рестарт, неполная погода, обновление measurements, отмена и временный DB сбой. Подтверждено отсутствие потерянных/дублирующихся публикаций. Worker исполняется напрямую; Compose wiring делает P6.

## P4 — Воспроизводимый исторический прогон

Ветка: `feat/p4-february-replay`.
Владение: новые `src/server/replay/batch/**`, `scripts/replay-february.*`, `tests/replay-batch/**`, `docs/handoffs/parallel-P4.md`.

Работа:
- CLI запускает последовательные выпуски с 31.01 по 28.02.2026 включительно, по одному заданному часу в явно выбранной timezone, для двух объектов и горизонтов 24/48.
- Параметры: asset IDs, approved model version, timezone/issue hour, диапазон, mode, resume ID. Сначала preflight inputs/coverage; никаких скрытых текущих forecast вместо архивных.
- Использовать существующие jobs/replay API, ограниченный polling, terminal failure/timeout/cancel; сохранять manifest выпуска, входные версии, forecast IDs и пропуски. Возобновление не дублирует завершённое.
- Экспорт прогнозов включает issuedAt/targetTime/lead/asset/model/weather provenance/unit. Мартовский хвост виден, но не входит в февральскую оценку.

Приёмка: тестовый adapter позволяет стартовать независимо от P1/P2; успешный диапазон, дырки, частичный сбой, рестарт и повтор запуска покрыты. Реальный PostgreSQL прогон проводится в P7. Synthetic manifest явно помечен и не считается официальным февральским результатом.

## P5 — Оценка после поступления факта и семантика

Ветка: `feat/p5-forecast-evaluation`.
Владение: `src/server/backtest/**`, новые `src/server/evaluation/**`, `scripts/evaluate-forecasts.*`, `tests/evaluation/**`, `docs/data-contract.md`, `docs/handoffs/parallel-P5.md`; новые миграции только `0105_p5_`.

Работа:
- Изолированная загрузка evaluation-only actuals и повторяемая оценка уже опубликованных прогнозов. Исправление факта создаёт новую версию оценки, не меняет прогноз.
- MAE/RMSE, N, покрытие и baseline на одинаковых парах; разбивка по турбине и lead/hour либо согласованным группам горизонтов. Зафиксировать правило учёта нескольких выпусков на один target, не считать случайные дубли.
- Оценка только февральских targets в явно выбранном календаре; no actuals → метрики отсутствуют. Отсутствие факта не мешает выпуску прогноза.
- Машиночитаемый semantic manifest: timezone, interval meaning, lag, координаты/mapping, единица/нормализация, подтверждённость и источник подтверждения. UNKNOWN не превращать в факт; исходные CSV не переписывать.
- Предоставить worker/CLI для обработки поступившего факта без изменения agent workflow. Автозапуск подключает P6.

Приёмка: эталонный небольшой расчёт метрик, N=0, пропуски, дубли, пересмотр actuals, мартовский хвост, защита от утечки targets; unit и disposable PostgreSQL tests. Получение отсутствующих реальных actuals — внешний blocker, не повод выдумывать результаты.

## P6 — Runtime wiring и реальный интерфейс

Ветка: `feat/p6-runtime-wiring`.
Владение: `src/server/agent/**`, `src/server/forecast/**`, `src/components/dashboard/client.ts`, новые adapter tests в `tests/runtime-wiring/**`, Compose/deployment файлы, `docs/handoffs/parallel-P6.md`.

Работа:
- Сначала создать тестируемое wiring через injected interfaces и контрактные doubles. После интеграции P2 подключить approved inference в обоих production путях: agent и synchronous forecast service. Не оставить один путь навсегда на persistence.
- После P3/P5 подключить workers в Compose с корректным стартом после миграций/healthcheck, секретами только из окружения, restart/shutdown. Не дублировать уже работающий dispatcher.
- Согласовать реальные API envelopes с dashboard adapter, убрать скрытый переход к synthetic при ошибке. Показывать фактическую модель/режим, missing inputs и причины недоступной оценки.
- LLM необязателен: проверенное объяснение/решение не должно обходить deterministic gates. Не обещать причинность изменения прогноза без evidence.
- Не редактировать незавершённую history UI другого исполнителя. Если client изменился в main, согласовать adapter с новой версией и сохранить её поведение.

Приёмка: persistence regression, trained model для обоих путей, LLM on/off/failure без обхода gates, real-envelope UI tests, Compose config/build и smoke после появления соседних модулей. До их появления task имеет статус integration pending, а не completed.

## P7 — Финальная сквозная приёмка (после P1–P6)

Ветка: `test/p7-agent-e2e`.
Владение: `tests/acceptance/**`, `scripts/demo-*`, package.json scripts, README.md, docs/demo.md, docs/acceptance.md, `docs/handoffs/parallel-P7.md`.

- Соединить import → weather ingestion → train/approve → automatic trigger → forecast → updated input → новая версия → replay → evaluation → export.
- Интегрировать требуемые существующим acceptance harness команды demo; документировать запуск с чистой disposable БД и повторный запуск.
- Проверить рестарт процессов, отсутствие дублей и утечки будущего, полный manifest всех запрошенных выпусков, API/UI на реальных ответах.
- Два независимых отчёта: synthetic integration smoke и официальный historical run. При отсутствии weather provenance/actuals/подтверждений официальный результат BLOCKED с перечнем недостающего; synthetic успех не снимает блокировку.
- Общий PASS означает выполненные требования кейса, воспроизводимые артефакты и проверенное происхождение данных, а не только успешную сборку.

## Проверки для каждого исполнителя

Запустить собственные поведенческие тесты, существующие затронутые suites, `npm run typecheck`, `npm run lint`, `npm run build`, `git diff --check`. PostgreSQL-изменения проверить на отдельной одноразовой БД, включая миграцию существующей схемы. Для docs-only работы достаточно проверки ссылок, структуры и diff; тесты приложения не выдавать за запущенные.

Если nested worktrees попадают в lint, использовать документированное исключение `.worktrees/**`, не скрывать ошибки приложения. Пересмотреть полный/staged diff, исключить секреты и generated artifacts. Фикстуры и mocks не являются доказательством доступности реальных внешних данных.

## Обязательная доставка в локальный main

Это явное указание для каждой задачи: **после реализации и проверки самостоятельно интегрировать её в локальный main**. Remote push не является условием этой поставки; недоступность origin не останавливает локальную работу. Нельзя объявить main обновлённым, оставив результат только в task branch.

1. Перед стартом проверить status/branches/worktrees, прочитать STATE.md, попытаться fetch и записать результат. Создать отдельную task branch/worktree от локального main, сохранив все его коммиты.
2. После проверок сохранить task-scoped handoff, закоммитить код. Зафиксировать task SHA.
3. **Интеграции последовательны.** Взять общий repo lock через атомарное создание каталога `parallel-main-integration.lock` внутри пути `git rev-parse --git-common-dir`. Записать владельца/время; если занят — ждать завершения владельца, не удалять чужой lock по таймеру. Освобождать только собственный lock в finally.
4. Под lock перечитать текущий main. Создать отдельный integration worktree/ветку от него; merge task branch, осмысленно разрешить конфликты, согласовать STATE.md с общей реализацией и другими активными задачами. Повторить затронутые проверки и review.
5. Найти worktree, где checkout main. Если он чист, выполнить там только `git merge --ff-only <integration-branch>` (никакой разработки в нём). Если main нигде не checkout — допустимо атомарно передвинуть ref через `git update-ref refs/heads/main <integration-sha> <old-main-sha>` после проверки ancestry. Никогда не применять update-ref к main, checkout в другом worktree.
6. Если checkout main грязный: не stash/reset чужие изменения. Fast-forward допустим лишь если Git сохраняет их без конфликтов; при пересечении путей оставить validated integration commit, записать `LOCAL_MAIN_INTEGRATION_BLOCKED` и конкретные конфликтующие файлы. Повторить после освобождения файлов, не заявлять завершение.
7. Если main изменился параллельно вне lock — обновить integration branch из нового main, повторно согласовать состояние и проверки; только fast-forward, без force/reset.
8. Проверить `git merge-base --is-ancestor <task-sha> main`, актуальный main SHA и присутствие артефактов. Не удалять worktrees до приёмки.

Отчёт исполнителя: что реализовано; точные PASS/FAIL/BLOCKED checks; ветка/task SHA; **локальный main SHA и результат проверки ancestry**; внешние blockers; следующий шаг. Не утверждать origin/main без отдельной успешной проверки.

## Готовый запрос для запуска задачи

> Выполни задачу P<N> из docs/parallel-agent-completion-spec.md. Работай автономно в отдельной task branch/worktree от актуального локального main, соблюдай владение файлами и общие контракты. Соседние задачи исполняются параллельно. Реализуй полный scope своей задачи, запусти проверки, обнови handoff; затем через отдельный integration worktree и общий lock сам интегрируй проверенный результат в локальный main. Сохрани чужие изменения. Верни task SHA, main SHA и проверку ancestry. Недоступность origin не блокирует локальную поставку; реальные недостающие данные и незавершённое wiring явно обозначай BLOCKED/integration pending. Не заявляй общий E2E до P7.

Запуск: шесть независимых исполнителей с P1, P2, P3, P4, P5, P6; после их интеграции — P7. Это ТЗ не является командой автоматически запустить исполнителей.
