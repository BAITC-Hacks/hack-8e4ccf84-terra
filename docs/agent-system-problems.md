# Проблемы агентной подсистемы приложения

## 1. Область проверки

- Проверенный код: `src/server/agent/**`, `src/server/jobs/**`, `src/server/replay/**`, `scripts/job-dispatcher.mjs`, `app/api/internal/jobs/tick/route.ts`, агентные API-контракты и тесты `tests/agent/**`.
- База проверки: `origin/main`, коммит `8895ba8` от 23.09.2026. Коммиты `e5b61c4..8895ba8` повторно проверены; production-код агента в них не изменён.
- Основание: FR-08, FR-09, FR-11, разделы 9–10 и AC-04–AC-12 технического задания `wind-platform-technical-specification.md` версии 1.1; `docs/hackalem-ai-agentic-wind-forecasting.md` использован как локальная копия требований кейса.
- Не проверялись: визуальное оформление, страницы дашборда, импорт CSV, ML-математика и бэктест вне точек интеграции с агентом.

## 2. Итоговый статус

Агентное ядро существует как изолированная библиотека и проходит fixture-тесты, но не подключено к runtime приложения. На текущем `main` невозможно выполнить полный сценарий:

`событие → постановка задачи → tick → инструменты → прогноз → публикация → журнал → ожидание следующего события`.

| Область | Статус | Факт |
|---|---|---|
| Очередь, lease, checkpoint, fencing | Частично готово | Реализованы memory/PostgreSQL stores и unit-тесты |
| Агентный workflow | Частично готово | Реализована фиксированная последовательность шагов |
| Production runtime | Не реализован | Нет сборки `JobRunner + PostgresJobStore + AgentPorts` |
| Защищённый tick | Не реализован | Endpoint всегда возвращает `idle` |
| Автоматические триггеры | Не реализованы | `triggerInput` нигде не вызывается приложением |
| Реальные инструменты | Не реализованы | Есть только TypeScript-интерфейс `AgentPorts` |
| Агентные API | Не реализованы | Нет `/api/v1/jobs/{id}` и `/api/v1/agent-runs/{id}` |
| LLM-решения и fallback | Не реализованы | Продуктовый workflow жёстко задан массивом `STEPS` |
| Replay end-to-end | Не реализован | Есть только in-memory virtual clock helper |

## 3. Найденные проблемы

### AG-001 — P0 — защищённый tick не выполняет задачи

**Факт:** `app/api/internal/jobs/tick/route.ts:1-4` всегда возвращает `{ "status": "idle" }`. Endpoint не создаёт `JobRunner`, не получает задачу из PostgreSQL и не выполняет шаг.

**Влияние:** `scripts/job-dispatcher.mjs` вызывает пустой endpoint. Автономный пересчёт, восстановление после перезапуска и обработка очереди невозможны.

**Требуемое исправление:** создать server-only runtime и вызывать `await runner.tick()` из endpoint. Ответ должен различать `idle`, выполненный шаг и безопасную ошибку.

**Приёмка:** задача в состоянии `queued` после одного tick меняет состояние или checkpoint ровно на один шаг; при пустой очереди возвращается `idle`.

### AG-002 — P0 — отсутствует production-реализация инструментов агента

**Факт:** `src/server/agent/ports.ts:33-51` объявляет `AgentPorts`, но в приложении нет объекта, реализующего этот интерфейс. Поиск production-вызовов `new JobRunner`, `new PostgresJobStore` и реализаций методов портов не даёт результатов.

**Не реализованы:**

- `fetchWeatherRun`;
- `listObservations`;
- `buildFeatures`;
- `predict`;
- `compareForecasts`;
- `evaluateWhenActualsArrive`;
- `explain`;
- `publish`.

**Влияние:** workflow исполняется только на тестовых заглушках из `tests/agent/workflow.test.cjs`.

**Требуемое исправление:** реализовать адаптеры к PostgreSQL observations/snapshots, погодному хранилищу, существующей ML-модели и транзакционной публикации прогнозов.

**Приёмка:** agent workflow выполняется на сохранённых данных без fixture-портов и публикует прогноз через production forecast store.

### AG-003 — P0 — автоматические и ручные триггеры не подключены

**Факт:** `src/server/jobs/triggers.ts:11-27` содержит `triggerInput`, но production-код его не вызывает.

**Отсутствуют источники запуска:**

- новый допустимый погодный прогон;
- новые разрешённые измерения;
- расписание;
- ручной запуск;
- событие появления факта для оценки.

**Влияние:** FR-08 и AC-07 не выполняются; новая версия без ручного вмешательства не создаётся.

**Требуемое исправление:** определить точки вызова триггеров, зафиксировать `issuedAt`, `eventKey`, модель и конфигурацию до enqueue. Повтор одного события должен возвращать существующую задачу.

**Приёмка:** первое событие создаёт одну задачу и одну forecast version; повтор идентичного события не создаёт новую задачу или версию.

### AG-004 — P0 — отсутствуют API задач и журнала агента

**Факт:** в эффективном App Router `app/` отсутствуют маршруты:

- `GET /api/v1/jobs/{id}`;
- `GET /api/v1/agent-runs/{id}`;
- ручной enqueue агента;
- управление replay.

**Влияние:** нельзя получить прогресс, результат, причину ошибки и последовательность инструментов. UI-контракты существуют, но сервер их не обслуживает.

**Требуемое исправление:** добавить защищённые read endpoints и ручной enqueue. Ответы должны использовать единый контракт статусов и безопасных ошибок.

**Приёмка:** по `job_id` доступны состояние, progress, result/error; по `agent_run_id` доступны шаги в порядке `sequence`.

### AG-005 — P0 — продуктовый агент не получает погодные данные

**Факт:** `fetch_weather_run` существует только как имя шага и интерфейс. В `STATE.md:18` зафиксировано отсутствие S03 weather adapters.

**Влияние:** агент не может выбрать допустимый погодный прогон, проверить `published_at/available_at` на реальных данных или применить резервный прогон.

**Требуемое исправление:** подключить сохранённые неизменяемые weather runs с полями источника, времени публикации, времени доступности, горизонта, значений, единиц и checksum исходного ответа.

**Приёмка:** прогон с `available_at > issued_at` отклоняется; допустимый архивный прогон воспроизводимо выбирается без сетевого запроса.

### AG-006 — P0 — отсутствуют agentic-решения, fallback и продуктивный LLM

**Факт:** `src/server/agent/workflow.ts:5-8` задаёт неизменяемую последовательность `STEPS`. Ветвей выбора резервного прогона, кэша, baseline или остановки нет. `explain` является необязательным callback без production-реализации.

Отдельный OpenAI SDK-код в `src/agent/**` обслуживает demo-домен `Case reviewer` из `src/domain/demo/config.ts`; он не связан с ветровым прогнозом и не предоставляет инструменты FR-08.

**Влияние:** требования FR-08 о выборе разрешённых действий и передаче LLM структурированных сводок не выполнены.

**Требуемое исправление:** реализовать ограниченную policy-модель решений. Временные, quality, authorization и publication gates должны оставаться детерминированным кодом. LLM разрешено выбирать только из валидированных действий и формировать объяснение.

**Приёмка:** при недоступности основного источника агент выбирает только заранее допустимый fallback; LLM не может разрешить прогон, отклонённый кодом.

### AG-007 — P1 — checkpoint и событие журнала фиксируются несогласованно

**Факт:** в `src/server/jobs/runner.ts:35-40` сначала вызывается `store.advance`, который снимает lease и переводит задачу дальше, затем отдельно вызывается `appendEvent`.

**Ошибка:** если `appendEvent` падает после успешного `advance`, catch вызывает `fail` со старым lease. `fail` возвращает `false`, потому что задача уже не `running`. Шаг выполнен, но событие `completed/fallback` теряется без повтора.

**Влияние:** журнал не является полным доказательством выполненных инструментов; нарушается FR-08.

**Требуемое исправление:** сохранять advance и событие атомарно в одной транзакции либо применять outbox/idempotent event append до подтверждения шага.

**Приёмка:** искусственный сбой записи события не оставляет задачу на следующем шаге без соответствующей записи журнала.

### AG-008 — P1 — ошибка heartbeat создаёт необработанный rejected Promise

**Факт:** `src/server/jobs/runner.ts:30-32` вызывает `void this.store.heartbeat(...)` без `await` и без `.catch()`.

**Влияние:** ошибка PostgreSQL в heartbeat не переводится в контролируемую потерю lease и может завершить worker через unhandled rejection.

**Требуемое исправление:** перехватывать ошибку heartbeat, прекращать дальнейшее подтверждение результата после потери lease и записывать безопасную диагностическую причину.

**Приёмка:** отказ heartbeat не завершает процесс и не позволяет worker с потерянным lease выполнить `advance`.

### AG-009 — P1 — входы агента проверяются недостаточно

**Факт:** `src/server/agent/workflow.ts:29-41` проверяет время, revision и список target timestamps. Типы `WeatherInput` и `ObservationInput` в `src/server/agent/ports.ts:3-16` не содержат достаточных метаданных.

**Не проверяются:**

- погодные значения и обязательные переменные;
- единицы измерения;
- source/checksum/input snapshot;
- принадлежность данных объекту;
- coverage и quality flags;
- разрешённая политика использования observation;
- согласованность station/turbine/line.

**Влияние:** типизированный интерфейс не гарантирует допустимость реальных входов.

**Требуемое исправление:** расширить входные DTO и детерминированную валидацию до построения признаков.

**Приёмка:** неподходящий объект, неизвестная единица, недостаточное покрытие и будущие данные отклоняются с отдельными кодами причин.

### AG-010 — P1 — результат прогноза допускает неподтверждённые единицы

**Факт:** `validatePrediction` в `src/server/agent/workflow.ts:43-58` проверяет количество, идентификаторы, timestamps и finite value, но не проверяет `ForecastPoint.unit`.

**Влияние:** агент может опубликовать `MW`, `MWh`, `null` или произвольную строку, хотя AC-16 запрещает неподтверждённый перевод мощности.

**Требуемое исправление:** проверять единицу против зафиксированного data/model contract и input snapshot.

**Приёмка:** прогноз с неизвестной или несовместимой единицей не публикуется.

### AG-011 — P1 — оценка факта выполняется в неправильной фазе

**Факт:** `evaluate_when_actuals_arrive` выполняется в каждом первичном workflow перед публикацией: `src/server/agent/workflow.ts:117-120`.

**Влияние:** будущий факт в момент выпуска обычно отсутствует. Отдельного возобновления оценки после его появления нет. Observation trigger создаёт полный новый прогноз, а не evaluation существующего forecast run.

**Требуемое исправление:** отделить forecast workflow от evaluation workflow. Событие поступления факта должно находить подходящие опубликованные точки и запускать только оценку.

**Приёмка:** появление факта обновляет evaluation, но не изменяет и не пересоздаёт историческую прогнозную версию.

### AG-012 — P1 — шаблонное объяснение не соответствует FR-09

**Факт:** `templateExplanation` в `src/server/agent/workflow.ts:60-66` содержит объект, горизонт, issuedAt, weather run и `meanDelta`.

**Отсутствуют:**

- изменившиеся входы;
- ограничения качества;
- покрытие;
- причина fallback;
- ссылка на текущий расчёт;
- ссылка на предыдущую версию;
- проверяемая ссылка на погодный прогон.

**Требуемое исправление:** формировать briefing из структурированных, проверенных полей результата. Не добавлять причинные утверждения без анализа влияния.

**Приёмка:** при отключённом LLM опубликован полный шаблонный briefing с теми же числовыми данными и provenance, что сохранены в forecast run.

### AG-013 — P1 — replay не является сохраняемой подсистемой

**Факт:** `src/server/replay/clock.ts` содержит только in-memory `VirtualClock` и функцию `revealReplayEvents`. Replay session, cursor, API и durable progress отсутствуют.

**Влияние:** после перезапуска виртуальное время теряется; невозможно гарантировать последовательное однократное раскрытие событий и показать две сохранённые версии end-to-end.

**Требуемое исправление:** хранить replay session, virtual time, набор событий и раскрытый cursor. Все replay jobs должны сохранять `mode=replay` и не попадать в live/backtest выборки.

**Приёмка:** replay переживает перезапуск, раскрывает минимум два события в порядке `availableAt` и создаёт две изолированные версии.

### AG-014 — P1 — статусы и отмена не соответствуют контракту

**Факт:** `src/server/jobs/types.ts:1` поддерживает только `queued | running | completed | failed`. ТЗ и UI-контракт используют `queued | running | succeeded | failed | cancelled`.

**Влияние:** API не может выдать ожидаемый статус `succeeded`, а пользователь не может отменить queued/running задачу.

**Требуемое исправление:** выбрать единый внешний контракт, добавить fenced cancel в `JobStore` и не публиковать результат после подтверждённой отмены.

**Приёмка:** queued задача отменяется сразу; running задача перестаёт продвигать checkpoint после потери права выполнения; API возвращает единые статусы.

### AG-015 — P1 — журнал не содержит обязательных эксплуатационных данных

**Факт:** `DecisionEvent` в `src/server/jobs/types.ts:49-57` не содержит duration, startedAt/finishedAt, source age, input coverage и отдельного безопасного error payload.

**Влияние:** не выполняются требования журнала и метрик выполнения из раздела 9 ТЗ.

**Требуемое исправление:** фиксировать timestamps и длительность каждого шага, attempt, fallback, result link, безопасный error code/details, возраст источника и покрытие.

**Приёмка:** журнал позволяет восстановить последовательность, продолжительность и причину результата без чтения серверных логов.

### AG-016 — P2 — в репозитории существуют две несвязанные агентные архитектуры

**Факт:**

- `src/server/agent/**` — детерминированный workflow ветрового прогноза;
- `src/agent/**` + `src/domain/demo/**` — универсальный OpenAI SDK workspace для демонстрационного `Case reviewer`.

В эффективных routes нет API универсального workspace; к ветровому workflow он не подключён.

**Влияние:** неясно, какой runtime является продуктовым; зависимость `@openai/agents`, approvals и generic repository не дают функциональности ветровому агенту.

**Требуемое исправление:** принять одно явное решение:

1. подключить SDK workspace как контроллер ветрового домена поверх детерминированных инструментов; либо
2. удалить/изолировать demo-код и реализовать только ограниченный explain/decision adapter внутри `src/server/agent`.

**Приёмка:** в README и коде существует один однозначный production entrypoint агента; demo-домен не попадает в production runtime.

## 4. Что уже работает

- Атомарный claim PostgreSQL через advisory lock и `FOR UPDATE SKIP LOCKED`.
- Lease token и fencing устаревшего worker.
- Checkpoint между шагами.
- Ограничение числа повторов и exponential backoff.
- Идемпотентный enqueue по event key.
- Идемпотентная публикация предусмотрена контрактом `publicationKey`.
- Проверка `availableAt/publishedAt <= issuedAt`.
- Проверка ровно 24/48 целевых часов и уникальности прогнозных точек.
- Шаблонное объяснение при сбое LLM.
- Разделение режимов `live/backtest/replay` в payload и publication key.

Эти пункты подтверждены unit-тестами, но пока не подтверждены полным production-сценарием.

## 8. Критерий готовности агентной подсистемы
