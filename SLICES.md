Slices реализации — прогнозирование выработки ВЭС

Основа: приложенное ТЗ «AI-платформа прогнозирования выработки ВЭС», версия 1.1 от 23.09.2026. Это
разбиение P0 для трёх участников, которые начинают одновременно. Порядок E1 → E2 → E3 → E4 → E5/E6 →
E7 → E8 определяет последовательность интеграции и приёмки, а не начала работы. Весь прикладной
код — Next.js + TypeScript и PostgreSQL.

редактирования общего файла.

Правила для всех slices

Ветка и отдельный git worktree на участника; внутри ветки отдельные коммиты на каждый его slice.
Изменять только файлы из своей зоны владения. Не редактировать чужие миграции, общие конфиги и
lock-файл. Изменение контракта оформлять предложением владельцу, а свой slice продолжать через
типизированный интерфейс или тестовую заглушку.

Один владелец интеграции принимает ветки по порядку зависимостей, запускает миграции и общие
проверки. Каждый разработчик начинает свои задачи до интеграционного gate.

Для каждого slice: сохранить промежуточный результат и краткую запись в своём файле прогресса после
каждого часа соревновательной части, если действует правило хакатона; приложить команды проверки,
фактический результат и ограничения. Секреты и исходные приватные данные не коммитить.

Не утверждать, что координаты, шкала мощности, точная схема CSV или архивная погода уже
подтверждены. До проверки использовать явную конфигурацию и маркировать допущения. Февральский
факт — только для оценки, пока организаторы не разрешат лаги.

В API ошибки имеют code, message, request_id, безопасные details; длительные операции возвращают 202
и job_id; повтор Idempotency-Key с тем же телом возвращает прежнюю задачу, с другим — 409. Все
времена хранения — UTC, исходная зона сохраняется в метаданных.

Контрактный gate перед сквозной интеграцией

S00 и S01 начинаются одновременно с остальными. S00 уточняет целевой объект, mapping, единицы,
временную шкалу, доступность данных и допущения. S01 закрепляет миграции, серверные типы и сигнатуры
сервисов в src/server/contracts/: Asset, Observation, WeatherRun, InputSnapshot, ModelVersion,
ForecastRun, Job, AgentEvent, EvaluationRun; DataPolicy, RunMode, IssuedAt, TargetTime; контракты
ObservationReader, WeatherRunReader, SnapshotBuilder, Predictor, ForecastRepository, JobStep,
EvaluationReader. Идентификаторы и точные поля согласовать с ТЗ, не выдумывать подтверждённые
значения. Модель ForecastRequest включает объект (ы), issued_at, горизонт 24/48, режим, разрешённую
версию модели и политику данных.

Контракты зафиксировать одним коммитом до объединения зависимых slices. Потребители с первого часа
делают свои тестовые реализации интерфейсов, затем подключают адаптеры; центральные контракты и
миграции самостоятельно не правят. Отдельный приёмочный gate — проверка соединения всех модулей на
одной точке T.

Порядок интеграции и границы конкуренции

Старт одновременно: S00 исследует данные; S01 публикует миграции, контракты и авторизацию; S02–S09
готовят свои модули на fixture. Ни один другой slice не меняет src/server/db/ **,
src/server/contracts/** или root-конфиги.

Gate B для объединения: S02 и S03 независимо поставляют канонические наблюдения и допустимые
погодные прогоны. S04 подключает только их публичные интерфейсы. S05 может готовить страницы на
fixture, затем подключить API. Результат E4 — работающий baseline → сохранённый прогноз → UI.

Gate C для объединения: S06 и S07 начинаются сразу, а подключаются к реальным входам после E4; S06
не владеет очередью и src/server/ml/baseline/**, S07 не меняет численную модель. Владелец S01
переносит согласованный вызов JobStep в защищённый tick endpoint. Затем S08 использует ровно тот же
путь прогноза; S09 завершает проверку.

При конфликте контракта или необходимости новой таблицы один владелец S01 вносит изменение в
миграции/типы и передаёт номер версии всем зависимым slices. Владелец S04 единолично меняет
публикацию forecast_runs/forecast_values; S07 вызывает его сервис, а S08 переиспользует его без
копирования формулы.

Что остаётся открытым по исходному ТЗ

Фактические данные resources/ ещё нужно изучить; расписание выпуска, точные координаты, уровень
измерения мощности, нормализация, часовой пояс и convention метки часа требуют подтверждения.
Погодный API нужно проверить на архив, фактические поля и publication delay. До получения
официальной метрики и формата сдачи действуют MAE/RMSE и внутренний CSV. Эти решения документируются
в S00/S03 и не заполняются догадками ради закрытия задачи.
