# Slices реализации — прогнозирование выработки ВЭС

Основа: приложенное ТЗ «AI-платформа прогнозирования выработки ВЭС», версия 1.1 от 23.09.2026. Этот файл — разбиение **P0** на задачи для параллельной работы. Порядок этапов ТЗ сохранён: **E1 → E2 → E3 → E4 → E5/E6 → E7 → E8**. Весь прикладной код — Next.js + TypeScript, хранение — PostgreSQL, без отдельного Python/backend-сервиса. P1/P2 не брать в работу до завершения P0.

## Правила для всех slices

1. Ветка и отдельный git worktree на каждый slice. Изменять только файлы из своей зоны владения. Не редактировать чужие миграции, общие конфиги и lock-файл. Изменение контракта оформлять предложением владельцу, а зависимый slice продолжать через типизированный интерфейс или тестовую заглушку.
2. Один владелец интеграции принимает ветки по порядку зависимостей, запускает миграции и общие проверки. Параллельность в таблице означает параллельную **разработку после указанного gate**, а не произвольный порядок merge.
3. Для каждого slice: сохранить промежуточный результат и краткую запись в `STATE.md` после каждого часа соревновательной части, если действует правило хакатона; приложить команды проверки, фактический результат и ограничения. Секреты и исходные приватные данные не коммитить.
4. Не утверждать, что координаты, шкала мощности, точная схема CSV или архивная погода уже подтверждены. До проверки использовать явную конфигурацию и маркировать допущения. Февральский факт — только для оценки, пока организаторы не разрешат лаги.
5. В API ошибки имеют `code`, `message`, `request_id`, безопасные `details`; длительные операции возвращают `202` и `job_id`; повтор `Idempotency-Key` с тем же телом возвращает прежнюю задачу, с другим — `409`. Все времена хранения — UTC, исходная зона сохраняется в метаданных.

## Контрактный gate перед параллельной реализацией

**S00 и S01 выполняются первыми.** В S00 фиксируются целевой объект (линия или турбина по фактической гранулярности), mapping, единицы, временная шкала, доступность данных и допущения. В S01 один владелец закрепляет миграции, серверные типы и сигнатуры сервисов в `src/server/contracts/`: `Asset`, `Observation`, `WeatherRun`, `InputSnapshot`, `ModelVersion`, `ForecastRun`, `Job`, `AgentEvent`, `EvaluationRun`; `DataPolicy`, `RunMode`, `IssuedAt`, `TargetTime`; контракты `ObservationReader`, `WeatherRunReader`, `SnapshotBuilder`, `Predictor`, `ForecastRepository`, `JobStep`, `EvaluationReader`. Идентификаторы и точные поля согласовать с ТЗ, не выдумывать подтверждённые значения. Модель `ForecastRequest` включает объект(ы), `issued_at`, горизонт 24/48, режим, разрешённую версию модели и политику данных.

Контракты зафиксировать одним коммитом до старта зависимых slices. Потребители могут делать тестовые реализации интерфейсов в **своих тестах**, но не править центральные контракты, миграции и публичные сигнатуры самостоятельно. Отдельный приёмочный gate — проверка соединения всех модулей на одной точке T.

## Порядок интеграции и границы конкуренции

1. **Gate A:** S00 фиксирует факты и неизвестные; S01 публикует миграции, контракты и авторизацию. Ни один другой slice не меняет `src/server/db/**`, `src/server/contracts/**` или root-конфиги.
2. **Gate B:** S02 и S03 независимо поставляют канонические наблюдения и допустимые погодные прогоны. S04 подключает только их публичные интерфейсы. S05 может готовить страницы на fixture, затем подключить API. Результат E4 — работающий baseline → сохранённый прогноз → UI.
3. **Gate C:** S06 и S07 реализуются параллельно **после E4**; S06 не владеет очередью, S07 не меняет численную модель. Владелец S01 переносит согласованный вызов `JobStep` в защищённый tick endpoint. Затем S08 использует ровно тот же путь прогноза; S09 завершает проверку.
4. При конфликте контракта или необходимости новой таблицы один владелец S01 вносит изменение в миграции/типы и передаёт номер версии всем зависимым slices. Владелец S04 единолично меняет публикацию `forecast_runs`/`forecast_values`; S07 вызывает его сервис, а S08 переиспользует его без копирования формулы.

## Что остаётся открытым по исходному ТЗ

Фактические данные `resources/` ещё нужно изучить; расписание выпуска, точные координаты, уровень измерения мощности, нормализация, часовой пояс и convention метки часа требуют подтверждения. Погодный API нужно проверить на архив, фактические поля и publication delay. До получения официальной метрики и формата сдачи действуют MAE/RMSE и внутренний CSV. Эти решения документируются в S00/S03 и не заполняются догадками ради закрытия задачи.
